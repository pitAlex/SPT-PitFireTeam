# Friendly Scav cargo

[Allegiance](../Allegiance.md#friendly-scavs) owns encounter selection and recruitment. This document owns the separate field-Scav cargo return. Saved squadmate kit, PMC follower loot and insurance remain governed by [Loadout Management](../Loadout-Management.md), [Looting](Looting.md) and [Follower Insurance](../Follower-Insurance.md).

## Admission and ownership

Only a successfully recruited, selected regular Scav in Allegiance can carry return cargo. Recruitment snapshots its starting kit. Successful player-commanded loose pickup, corpse loot and container loot mark the acquired item tree, including newly equipped gear. Transaction snapshots distinguish added stack units from the Scav's existing share. The Scav's starting kit, ambient bot loot and failed transfers are excluded. Field recruits cannot use View Backpack or Swap Gear; those interfaces are for saved teammates. Existing handover bookkeeping remains supported internally but is not a way to give a field recruit cargo. Extraction reads only the remaining live inventory, so dropped, consumed or withdrawn items are absent. Mixed-stack consumption conservatively consumes the acquired share first. Return serialization filters a flat copy without detaching live items.

The human PMC must finish alive as Survived, Runner or Transit with a nonempty native exit name. `LocalGame.Stop` captures before follower teardown. A recruited Scav qualifies if he is alive and still registered as a field follower of that human at capture time. His distance, native `Entered` membership and exit colliders are not consulted. A dismissed Scav, dead companion, follower of another player, unrecruited friendly, death or abandonment cannot deliver cargo. Multiple qualifying companions contribute to one return package. An empty ordinary-extraction package sends the same localized thank-you note as empty-handed transit, without items. Real co-op exits retain their native message/reward flow, including when gifts are disabled; empty cargo adds no separate note there. The capture never changes native extraction admission or countdowns.

### Transit departure

Recruited Scavs stay behind when the human transits; they are not added to the next map's follower spawn list. Transit settles their remaining command-collected cargo immediately against the departing map's native server ID, rather than carrying cargo provenance across maps or waiting for the human's later extraction. Fence sends the existing cargo message when eligible items remain, or a localized `scavTransitFarewell` note when none remain. The message is available after returning to the menus; no message UI is opened during map travel.

The client report explicitly identifies transit, and the server requires a matching native `TRANSIT` result and non-null location-transit data. A transit report cannot authorize a normal extraction result or vice versa. No recruited Scav means no transit message. Existing exact-ID cargo filtering, death/dismissal/betrayal exclusions, durable message receipt and insurance-report completion apply equally to empty notes and cargo mail. A later map starts with no departing companion/cargo registration, so its extraction cannot resend that settlement. Deleted or claimed completed messages are not regenerated.

Transit settlement adds no supplemental standing or random reward and does not enter the native co-op gift merge path. Existing ordinary-extraction standing and native co-op handling are unchanged. PMC field-recruit invitations, saved-squad returns and all follower transit selection/respawn rules are unchanged.

Broken trust blocks this capture immediately, including the interval before the deferred departure removes follower registrations. A departing Scav cannot grant the mod's cargo return or supplemental co-op standing by extracting during that interval.

This does not expand `InteractableObjects.IsReturnSquadMember`: field recruits cannot return starting kits through the saved-squadmate return flow. Savage followers continue to be skipped by `SaveFollowersProgress`, generating no roster invitation or saved Scav profile.

## Native co-op and SVM

Every normal extraction exit can simulate co-op for returning the Scav's remaining command-collected cargo. Extraction together at a non-co-op exit also grants a flat +0.025 Fence standing once per raid, regardless of cargo quantity or number of Scav partners. This does not diminish with repeat visits or advance native co-op counters. Ordinary exits add no random gift. Native requirements, timer and payment still apply. Transit departure is message/cargo settlement only, as described above.

Real co-op exits retain their usual native random Fence gift, original message wording and Fence standing gain. Eligible cargo is combined with that gift in the same package before the native notification is sent. Native `ScavCooperationRequirement.UpdateStatus` checks for a Savage participant and a non-Savage participant in `Entered`; neither predicate requires a human player. An NPC Scav therefore qualifies. The Scav retains its side and original role after follower conversion. Native diminishing standing gains and normal server gift configuration remain in control.

SVM's paid co-op override retains the exit name but changes it to a shared timer with a TransferItem requirement and a rouble price, removing the native need for a Scav. Stock Fence handling identifies co-op by membership in `InRaidConfig.CoopExtracts`. This feature still requires a living recruited Scav following the extracting human, including at paid exits. It does not impose an additional paid-exit proximity check. At real co-op exits, standing and random gifts remain entirely under native/SVM control. If SVM disables that reward flow, this feature still returns cargo but adds no replacement standing or random gift.

## Backend delivery and receipts

`AllegianceScavCargo` posts a capture through `/singleplayer/pitfireteam/scav-cargo`, bound to the native server ID. `FriendlyScavCargoService` persists it in that user's Allegiance database. Only the actual matching PMC end result, successful extraction or explicitly matched transit status and captured exit name authorize delivery; capture alone sends no mail. The first capture owns the raid and cannot be replaced by retries.

The service uses the same `InRaidConfig.CoopExtracts` exit-name classification as native raid completion. Actual co-op exits receive no mod standing adjustment. For other exits, the flat 0.025 gain is clamped to configured Fence limits and synchronized to PMC/player-Scav trader data. A per-raid `pitFireTeam/scav-coop/` receipt and its `/standing` result persist alongside standing in the native profile. The result uses integer millionths to preserve the six-decimal standing precision. If native raid completion imports the client's earlier Fence standing again, the matching callback restores the committed result, including after cargo completion and profile reload; it does not add another reward or send another package. On-disk receipt/result and standing verification precede cargo completion. Legacy flag-only receipts lack an authoritative result and remain excluded from a new award. Native co-op counts are never read or changed. No positive sound is played. See [Fence karma](../Fence-Karma.md).

The post-native end callback sends ordinary cargo returns with the localized `scavCargoReturn` wording (English: "One of my men brought your things back. Here’s your stuff, as promised."). Native co-op completion and Fence-gift calls use isolated execution-context scopes to associate only the matching successful PMC raid and captured cargo. The native gift generator, message choice and standing calculation still execute normally; `HandleCoopExtract` is not patched. Server-only HarmonyX 2.16.1 mail hooks combine the native reward and filtered cargo under the durable pre-reserved message ID before insertion/notification. Native gift items use normal processing, including ammo-box filling; cargo uses a separate native cloning/remapping pass with auto-filling suppressed, then joins the gift's stash. Unassociated gifts and other mail retain native IDs and behavior.

If there is no cargo, the native gift stays untouched. If no native gift is sent (including disabled SVM rewards), the end callback still sends the standalone return without creating a replacement random reward. Cargo preparation/merge failures leave the native gift intact and allow standalone cargo delivery to retry, with a warning. This fallback cannot identify the gift as a completed cargo receipt. Combined receipts persist both returned source IDs and the expected complete mail count; interrupted acknowledgement, claimed or deleted completed messages cannot regenerate the combined package.

Player-extracted items, BTR transfers and protected teammate trees are filtered out. Accepted returned IDs use the existing insurance cleanup to prevent a second insurance copy. The cargo report also completes the existing insurance report barrier, including rejected outcomes. The profile's Fence mail is saved and verified on disk before recording completion. Receipt replay and interrupted receipt writes reconcile against the same message ID; a completed/claimed message cannot generate another return. Global Fence gift options and co-op exit lists are never temporarily mutated.
