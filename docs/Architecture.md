## Lifecycle and invariants

`FriendlyEncounterPopulation` checks living ambient populations only when a successful roll requests a new friendship. `FriendlyEncounterPopulationPolicy` owns percentage rounding and the two-slot solo-PMC minimum. Only ordinary encounter selection uses this budget, without polling per frame, rerolling existing candidates, revoking established friendships after deaths, or changing follower ownership. Scav-companion neutrality retains its independent 75% group roll and trust history; it does not consume encounter slots or confer encounter/recruitment eligibility. See [Allegiance](Allegiance.md#finding-friendly-pmcs).

Core converts/recruits followers, assigns player ownership, reconciles groups/hostility, installs follower layers and releases state on dismissal/raid teardown. Saved squadmates and raid pickups share the follower framework, but differ in profile persistence and command eligibility; [Commands](Commands.md) owns those distinctions.

[AllegianceScavRelations](../client/Modules/AllegianceScavRelations.cs) keeps recruited Scavs in independent native groups, links reciprocal squad allies, applies raid-local Scav neutrality and publishes actual hostile relationships across allied groups. [AllegianceScavTrustDamagePatch](../client/Patches/AllegianceScavTrustDamagePatch.cs) captures the first damaging-hit relationship before native health/death and retaliation callbacks; the existing kill dispatcher owns trust loss. Deferred Scav betrayal departure retains native group identity, removes all departing companions before publishing hostility, and keeps special Scav roles excluded. See [Allegiance Scav groups](Allegiance.md#scav-groups-and-trust).

Allegiance recruited-follower kills reuse the existing `traitor` report. [FriendlyEncounterPenaltyService](../server/Services/FriendlyEncounterPenaltyService.cs) persists independent 24-hour penalties per user in the Allegiance database; [FriendlyEncounterPenaltyRuntime](../client/Modules/FriendlyEncounterPenaltyRuntime.cs) mirrors them for friendship rolls and the Roster label. Shared expiry/countdown arithmetic lives in [FriendlyEncounterPenaltyPolicy](../shared/FriendlyEncounterPenaltyPolicy.cs). See [Allegiance penalties](Allegiance.md#friendly-encounters-penalties).

[PMC karma](PMC-Karma.md) independently observes friendly kills, actual recruitment and raid completion. Core captures eligible bot identities before retaliation/cleanup; the server persists native PMC karma with deduplication receipts in the player profile, shared across modes. Spawned/saved squadmates and player-Scav/Fence standing remain outside this feature.

Config entries hold saved preferences. Gameplay consumers, Settings controls and server settings synchronization resolve mode-locked values through [GameplayModeRuntime.GetEffectiveValue](../client/Modules/GameplayModeRuntime.cs), independently of cfg edits/reloads. [Allegiance](Allegiance.md#settings-policy) owns its fixed values; [Gameplay modes](Gameplay-Modes.md#saved-settings-and-restoration) owns Guns for Hire snapshot restoration.

Core owns peaceful follow/request execution and post-combat recovery. Combat has one owner at a time; an absent/unready optional brain falls back to core. Optional callbacks may provide readiness, release/reset and passive data, but general compatibility cannot depend on the addon being loaded.

Optional mode registration can also supply immutable `CompanionGearPolicy` data. Core owns restricted donation planning, exact item/plate moves, inventory fit, provenance, rollback and ordinary-loot bypass guards; the addon chooses the role and restrictions. Going Rogue supplies the three Goons' fixed-kit policy without a Core dependency on its assembly. See [Give Gear](Give-Gear-Spec.md) and the [Going Rogue profile/gear contract](../going-rogue/README.md#mode-and-profiles).

An optional `CompanionCommandPolicy` separately supplies combat point willingness, a push-confidence function and an optional target-role relative combat-power multiplier. The original two-argument policy constructor remains available and neutral. Core owns target admission, known-contact threat inputs, command storage, response and ordered execution; Going Rogue owns the Goon role mapping/confidence formula. Its autonomous selectors reuse the same addon mapping and Core's known-contact counter/shared threat formula without requiring a Core dependency on their assembly. Registration replacement/removal clears this provider, and other modes/roles retain their ordinary command rules. The original mode-registration signature remains unchanged.

An optional advance-order provider receives `CompanionAdvanceOrderContext` after target admission, with one broadcast sequence and an evaluator for the existing Core confidence path. Going Rogue uses it for shared Knight verdicts and local Big Pipe delegation. Replacement/removal clears the provider; failures refuse the push. Core also provides a non-publishing assigned-point planner and an admitted-target prepared transition for explicit mission replacement, preserving living contacts and rolling back the goal if preparation fails. The addon owns leadership state; Core retains target, navigation and action publication gates. See [Going Rogue command hierarchy](../going-rogue/docs/Knight-Combat.md#combat-command-willingness).

The optional [Going Rogue Knight and Big Pipe brains](../going-rogue/docs/README.md) use an internal `FollowerCombatLayer` constructor to supply its combat logic/action factory, with friend-assembly access for the jointly shipped addon. Core has no reverse assembly dependency. `FollowerCombatSupportPlanner` shares Rifleman's existing push/engagement planning without sharing either brain's general selector. The addon shares Goons eligibility/readiness/lease handling while retaining each role's selector and native strategy; it restores the original native/external owner on release. Big Pipe's launcher opportunities use Core's planned grenadier objective; Goons are not registered for Core's general Rifleman fallback. Native active bosses own their BossLogic tick; legacy human-leader forwarding is reserved for bosses without native ticking.

Saved follower activation uses a validated metadata snapshot and bounded registration/readiness barriers. Native creation can finish during loading while the actor remains `NonActive`; Core waits for the captured game's `GameStatus.Started` before starting the eight-second registration deadline. Loading waits stop on raid replacement, death or stopping; known registration failures propagate immediately. Combat readiness and the delayed Ready phrase also recheck the captured raid. Optional mode callbacks acknowledge their own combat owner and release it on failed setup; Core owns retries, native actor rollback and localized failure reporting. Unknown optional-mode selection is conservative until validated. [Going Rogue spawning](../going-rogue/docs/Knight-Combat.md#raid-allegiance-and-spawning) describes its character policy. Runtime teardown does not turn a failed spawn into a saved death/escape outcome.

Core passively captures exceptions discarded by EFT's native activation catch for pending follower registrations. The verified catch entry consumes the exception through a non-throwing logger and leaves native activation/state handling intact; ordinary bots are excluded. A changed catch layout disables capture with a warning rather than rewriting unknown IL. This exposes the original failing subsystem without calling activation or other providers again.

Core also owns native human-leader activation compatibility. `FollowerHumanPatrolChooserPatch` keeps native `BotFollower.SetToFollow` and follower mode, translating an AI-group chooser request to the ordinary chooser only for followers linked to the local `pitAIBossPlayer`. This avoids native Big Pipe/Birdeye patrol code dereferencing a human's absent AI owner; native AI-led groups and authored patrol-data precedence remain unchanged. `FollowerNativeBrainActivationPatch` preserves the native role/brain of pre-marked or registered Goons through SPT's brain-activation prefix and its paired postfix state. Their USEC/BEAR presentation side must not put them into PMC-only brain-weight lookup. Other roles and unmarked raid actors retain SPT's behavior; no side or role mutation is used to make registration succeed.

The shared cover lifecycle is selection, travel, arrival, hold, then a concrete next decision. Immediate fire, pressure/recent hits, ally or boss protection and compromised cover can preempt a hold. Distance regroup is a fallback after productive combat/commitments. Heal-cover arrival yields directly to treatment. [Combat tactics](Combat-Tactics.md) defines the detailed priority and timing.

Per-follower proficiency uses independent data/settings; no global preset is edited to tune one follower. [Proficiency](Friendly-AI-Performance-Settings.md) owns Vision, Precision and Reaction. Tactical aggression is a separate input.

## Server responsibilities

The server owns mod teammate profiles, persistence, customization, social/group integration and raid outcomes. Teammates are mod-owned profiles, not full independent stock `SptProfile` accounts. Runtime bot spawning is a client/game-session responsibility. For mode companions with fresh per-raid generation, Core prepares and reserves generated/provisioned equipment at MatchMaker AcceptScreen, before refreshing native group/profile previews. The party preparation, per-member join revisions and mode generation scope the reservation. Kicking and re-inviting one member generates a new kit only for him, and entering loading retains the prepared kits; actual spawn clones the same equipment onto the current saved identity/skills/health, without reprovisioning or rerolling it. Native generation receives the selected map/time configuration in a restored temporary generation context. Transit uses carried profiles. Core persists an isolated copy of each generated/provisioned raid inventory into the saved profile for native equipment viewing. This inventory-only update uses the existing raid-result persistence lock and current roster record; it never turns the preview into the next raid's loadout. Companion skill baselines come from native generation; an optional addon migration callback may correct older profiles once, with its actor/version receipt committed in the same profile save. Later equipment generation preserves stored skill progression. See [Going Rogue profiles](../going-rogue/README.md#mode-and-profiles).

[Teammate health](Teammate-Health.md) owns HP-only raid snapshots, original-spawn-maximum normalization, native post-raid penalties, effect clearing and atomic health receipts. Saved-teammate activation preserves the recovered spawn HP; transit retains its native carried state.

[FriendlyPmcArmbandHooks](../server/Services/FriendlyPmcArmbandHooks.cs) enforces the enabled PMC Faction Arm Bands setting on the returned `BotInventoryGenerator.GenerateInventory` inventory, after stock or replacement generation. Startup, settings endpoints and the hook share the singleton [FriendlyServerSettingsService](../server/Services/FriendlyServerSettingsService.cs), so the hook sees both the loaded preference and later toggle changes independently of shared SPT config writes. It sets blue USEC/red BEAR equipment, adds a missing band and removes replaced band trees. Disabled settings, player Scavs, non-PMC bots and existing saved inventories are unchanged. No Acid assembly dependency or tier-pool mutation is required.

## Development boundaries

Gameplay-mode addons can claim companion combat by native role. Core excludes those actors from SAIN addon tactic/command selection before runtime preparation, without changing stored preferences or ordinary followers.

An optional quest-companion map policy scopes Core's automatic boss selection to implemented addon tasks. Core requires an empty selected group, PMC side and Going Rogue; the addon owns quest/map admission. The existing follower-generation route can also request a temporary quest companion: server mode/role policies independently validate active quest, map, selected-member count and native readiness, then reuse boss equipment provisioning without creating a roster/default-loadout record. This path is separate from saved-party inventory reservations. See [Going Rogue quests](../going-rogue/docs/Knight-Quests.md#quest-companion-deployment).

Core Marksman offers an optional companion-position callback at fresh planning, after survival, close-weapon, arrival/commitment and player-support branches. Ordinary Marksman construction retains the existing behavior. Going Rogue's [Birdeye brain](../going-rogue/docs/BirdEye-Combat.md) supplies only native sniper geometry and Knight assignments there; Core continues to own secondary preparation/return, action publication and arrival termination.

Build/reference policy is in [SPT compatibility](SPT-Compatibility.md). Machine-local paths, release packaging destinations and the bug tracker are in [LOCAL.md](../LOCAL.md). Commands, looting, UI and storage each have one owning topic; avoid copying their full contracts into this overview or AGENTS.md.
