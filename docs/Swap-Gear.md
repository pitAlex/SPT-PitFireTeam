# Swap Gear

Core owns the manual in-raid editor. This is separate from add-only commanded [looting](looting/Looting.md) and the out-of-raid [loadout editor](Loadout-Management.md).

## Interaction and draft

- Same 2.5 m / 18-degree targeting as View Backpack; eligible targets are the player's living active spawned or recruited followers. No backpack required.
- Opens only from battle UI while the follower is peaceful and neither inventory is busy. Healing, loot work, combat, invalidation, distance or player death interrupt the draft.
- Opening checks the active native weapon record's reload state, not every cached weapon record. EFT updates the active record; a stale reload flag on a stowed weapon cannot by itself block the editor. Native hands/interaction, weapon-change, grenade and danger gates still apply.
- Rejected openings log `[SwapGear][OpenRejected]` with the exact first safety reason, resolved/native target, membership, request and raw hands/inventory state plus bounded owned-candidate distances. The generic user warning is unchanged. Diagnostics do not repeat safety, medical or hands-provider calls and never clear enemy or inventory state.
- Two independent cloned inventories preserve item IDs and state. The editor rejects any clone that shares a live item reference. Changes to clones cannot affect either actor's live equipment, item provenance, armor effects or weapon bindings.
- Apply Changes is centered horizontally above the helmet slot, between LOOT and the follower's name in the header row. It clones the inventory Back button's native textured hover/pressed artwork, text animation and hover/click sounds, using the name's font size with bold text. The native name and LOOT layout stay unchanged. Closing/escape before Apply discards the draft. No custom shared-key/voice timing behavior is added.
- Follow/patrol uses its existing inspection hold; native weapon-manager ticks are held while editing so automatic reload/repacking cannot race the draft. Combat interrupts the session rather than freezing the world.

## Access policy

Backpack contents suppression preserves the equipment row when the native searchable-content component shares its root. Closing content UI must not disable the backpack header/icon/drop target. `[SwapGear][BackpackUI]` reports eligibility, deleted/allowed state, row creation/activity/layout and shared-root suppression for runtime diagnosis.

Native `UIElement.Close` deactivates its GameObject. Suppression now reactivates a shared row root without creating contents grids. Seven production-helper fixture assertions cover shared/separate/ancestor/standalone objects and direct content hooks; 235 total Gear Swap/quick interaction/reload assertions pass. The actual runtime object hierarchy and cause remain unconfirmed until the new row diagnostics are captured in raid.

Visible follower slots: FirstPrimaryWeapon, SecondPrimaryWeapon, Holster, TacticalVest, ArmorVest, Headwear, FaceCover, Eyewear and Earpiece. The holster can be emptied, filled or exchanged for both spawned and recruited followers, including pistol attachments and seated magazines. Spawned squad followers additionally expose Backpack, including an empty backpack slot. Eligibility uses the existing saved/transit-aware `IsSpawnedSquadMate` identity; recruited followers use the same nine-slot base policy without Backpack. Scabbard, pockets, secure container, armband, dogtag and special slots remain unavailable, even when empty. Filtering is per cloned controller/root, never a global slot-list change. The player's normal slot layout is preserved.

The spawned follower's backpack can be removed or exchanged only as a whole item tree, retaining every contained item. Its grid and any special child slots are not created in the editor. Open/double-click is blocked; source/destination ancestry checks reject adding, removing or rearranging contents, including nested containers and shortcuts. A backpack that occupied the follower slot stays sealed for the rest of this draft even after moving to the player's side, preventing a remove/open bypass. Unrelated player backpack contents remain editable. Replacement bags become sealed after handover; Apply replays this sealing in operation order so preparing a player backpack before handover remains valid. Existing ownership/protection/return tracking includes the full transferred tree. Backpack contents retain their existing cargo classification.

Applying a removal may leave the follower without a backpack. A replacement can be equipped through a later Swap Gear session or the existing loose-item quick/voice pickup command, whose native pickup order tries compatible empty equipment slots before cargo. This command retains its existing follower assignment and safety rules and does not replace an occupied backpack slot. No automatic bag upgrade or content repacking is introduced. Cancel leaves both live backpacks and contents unchanged; nothing transfers before Apply.

All vest contents can be transferred, including ordinary valuables. Whole rigs can move with their contents. An armored rig can be exchanged for separate armor and a tactical vest (and vice versa), moving magazines into the new vest in the draft. Individual armor plates can also move through normal compatible slots. Vanilla's equipped-carrier raid lock is bypassed only for editable cloned armor slots and the validated synchronous Apply replay, so a carrier need not be temporarily unequipped to replace its plates. The inspection UI removes that lock only on editable clones. Permanently locked/built-in inserts, compatibility filters, hidden inventory restrictions and normal live inventory behavior remain unchanged. Cancel and close end the exception; no template or global raid-state flags are changed.

Source and destination ancestry checks also cover shortcuts, nested containers and empty hidden slots. Discard is denied at the native operation boundary as well as the menu. Only inventory editing interactions are exposed: inspect/open, equip/unequip, install/uninstall, load/unload whole items and fold/unfold. Moving, swapping, splitting, merging, stack transfer and folding have replayable edit records. Consuming, repairing, insuring, magazine-preset/ammo loading actions, tagging and other non-editor operations are not replayed. Only the Gear tab is accessible during the session.

Draft conversion uses a local-only `AbstractOperation` token, not EFT's normal async operation constructors. Those constructors publish `Begin` during construction; using them alongside the draft's own Begin/Succeed pair leaves stale busy events. Only `Stage` owns draft event publication. Draft tokens cannot serialize or send backend commands.

In-raid removal/reinsertion, compatible plate replacement, Apply/cancel and unchanged vanilla inventory still require runtime qualification.

Pressing Apply hides the entire button and shows the native item-thumbnail loading indicator in its place and displays "Please do not close until the transfer process is finished." A correctable draft validation failure (no complete firearm or insufficient magazine landing space) keeps the editor and all staged edits open, hides the progress feedback and restores Apply so the player can correct the arrangement. No live items or hands have changed at that point. Once hands transitions begin, the indicator and message remain through transfer and both actors' hands restoration. The screen closes automatically when that work finishes, including recovery after a rejected transfer. Closing manually during Apply still cancels safely before replay; wait for automatic closure to complete an exchange.

1. Revalidate safety and compare serialized live equipment with the opening snapshots. Reject stale drafts without overwriting live damage, consumption or other inventory changes.
2. Validate the final follower arrangement: at least one complete firearm remains. Each externally loaded firearm's seated magazine must fit the actual free tactical-vest or pocket cells. The native location search checks contiguous geometry, rotation and compatibility, including free columns within partially occupied larger grids. Reloads are sequential: all three firearm slots may share one landing opening if every magazine fits it independently. A carried spare is already occupying cells, not an additional simultaneous ejection reserve. Empty intermediate slots are allowed. No weapon-value upgrade comparison or pickup-category setting applies.
3. Release player and follower hands, then revalidate. Hands transitions wait for EFT's process and weapon-change lock both before requesting and after receiving the callback. Continuations cannot run inline within the native callback, which occurs before EFT releases its process lock. Each transition has a ten-second deadline; success with an unexpected controller/item is retried at most three times. Closing or danger during this phase cancels before item transfer.
4. Replay the staged operations on the original items, on Unity's thread without yielding. Every completed native operation provides rollback data. A failed operation or mismatch with the accepted draft rolls back completed operations in reverse order before publication. Rollback failures are logged and reported distinctly; no success claim is made.
5. Record existing ownership/return rules and publish native inventory events for visuals, armor and weight. Refresh weapon records for every firearm slot, remove stale records, select a complete main firearm and refresh grenade selection. Before restoring each actor's hands, wait for native body-slot model loading to finish, resampling jobs as equipment events replace them. After restoration, wait again and verify that the held firearm's equipment slot has neither a body item nor a holstered model. Each model-loading wait is bounded to ten seconds, retains Unity's context and reports faults; a pre-restoration loading failure still attempts hands recovery without claiming full success. Restoration verifies both the callback item and the actual live hands item, including a firearm controller for weapons. A player giving away their last firearm uses the explicit empty-hands path. Native follower binding failure is reported rather than accepted as success. Grenade-use permissions are not enabled by giving grenades.

Only the synchronous replay scope treats accessible live items as searched/known for transfer validation. After successful transfer, acquired item trees get address-specific known/search state through the existing backpack helper. No permanent template examination is granted.

The global examination hook checks the active commit scope before reading item addresses. Detached preset roots use nullable `CurrentAddress`; native `Parent` throws for these items. Address ancestry and hands-restoration checks also tolerate detached roots.

All opening, stale-live and accepted-draft/replay snapshots canonicalize only each grid descriptor's `ContainedItems` collection by ordinal item ID. EFT serializes dictionary enumeration order, which can differ between a compact clone and a live grid with removed-entry holes. This order is not inventory state. Every item's identity, template, stack, components, child tree, grid, coordinates and rotation remain checked; slot, cartridge/stack and component array ordering is unchanged. Missing or duplicate grid IDs fail closed. Normalization touches serialized descriptors only, never live items or grid collections.

If replay differs from the accepted draft, passive `replay-mismatch` diagnostics capture both canonical equipment states before rollback. Each affected actor logs the exact JSON path, owning item ID/template and actual/expected values, bounded to 24 differences plus an omission marker and 384 characters per value. Parsed equality with different serialized text is identified separately. These diagnostics do not alter comparison, transfer or rollback behavior.

## Ownership

Return eligibility first requires a saved squad member. Field recruits never enter the return-item path, including after gear exchange; their retained live equipment can become part of a later recruitment invitation without also being mailed to the player. For squad members, equipment occupying a gear slot is kept regardless of loadout mode or earlier player-owned cargo tracking. This includes restoring a previously removed backpack. Slotted attachments, plates and seated magazines/ammunition stay with equipped gear; grid contents and pocket contents retain their existing cargo-return rules. Existing [protection rules](Loadout-Management.md#protected-extraction-filtering) still apply to Restricted gear owned by other teammates.

Return tracking includes descendant fallback IDs for plates, attachments and magazines, since these can later leave their initial parents. Final mail and equipment snapshots apply the same equipment-versus-cargo filter; a tracked equipped container keeps its shell without swallowing separately returnable contents. Existing collection deduplication prevents nested duplicate mail. Taking tracked items back removes their follower return entries; only previously return-tracked IDs are removed from protected-raid tracking. Split stacks inherit source provenance. Merging or transferring between player-owned and follower-owned stacks is rejected: keep them separate so a single resulting item ID cannot incorrectly combine different return/protection rules. Existing in-raid loose-ammunition lineage limitations outside this editor remain unchanged.
